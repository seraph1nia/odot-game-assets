# Reference calibration, baselines and bounded acceptance

Use when deciding whether guidance/refinement is useful, not merely whether a
validator returns success. Visual criteria belong to the selected
[D-rule owner](../design/index.md); this leaf owns the evidence procedure, not a
second list of design thresholds. Implementation/check facts remain in
[pipeline](../pipeline/index.md). No asset work is authorized by this procedure.

<a id="calibration"></a>
## Calibrate a criterion without manufacturing authority

1. Select the existing [reference ID/crop](../references/index.md) and
   [evidence anchor](../references/evidence.md). Open the image itself.
   Separate observed convention, chosen project adaptation and measurable contract.
2. Use inspected existing pictures for qualitative pass anchors/fail criteria.
   F4/F6 visible cap facets coexist with the approved selective-softness adaptation;
   don't pretend smoothness was extracted from all pictures. Dreaming fauna are
   authored adaptations, not supplied-match exemplars.
3. For a proposed numerical landmark/value/bevel/glow/resource target, describe
   measurement convention and uncertainty first: exclude equipment/base from body
   ratios; compare comparable surface regions; record view/light/pose; inspect
   actual occupied size. Unknown albedo/roughness/animation/rights cannot be read
   off stills. Keep actual game view envelope and D08 tiers explicit/provisional.
4. Use existing references/previews first. New fixture renders/crops/maps or asset
   experiments need separate authorization; preserve originals and derivative
   provenance/rights scope. Guidance-only work links originals/coordinates, not
   new raw reference copies or a fabricated calibration result.
5. If an art metric becomes accepted/executable later, update its existing owner
   once and link the symbol from the D-rule; don't copy constants into family/
   recipe leaves. Record revision/reason/scope in the design index. Artist acceptance
   and native performance are evidence to acquire, never implied by guide adoption.

<a id="baseline"></a>
## Baseline and refinement acceptance (later authorized work)

1. Record source revision; selected canonical ID; source/GLB/map hashes; library/
   dependency state; standard revision and exceptions. Preserve manual sources,
   packed/unpacked maps and before outputs. Missing old before caches must not be
   relabeled as available historic evidence.
2. Predeclare the changed-rule hypothesis: e.g. D01 lookout separation or D05
   planted contacts. Record expected benefit before changing the asset.
3. Establish matched profiles through [review scenes](../blender/review-scenes.md):
   source/portable/target purpose, camera/elevation/ortho scale, lighting/world,
   color management/exposure, bloom, image dimensions/occupied height, pose/frame.
   Older saved previews can be diagnostics but not automatically matched baselines.
4. Compare before/reference/after at full and actual/provisional target sizes.
   Add silhouette/grayscale/glow-off companions only where relevant. Judge the
   complete composition, not a favorable tiny crop in isolation; reference lighting
   remains unknown. Unit motion appeal needs normal-speed clips, not still scores.
5. For each applicable D-rule record **pass / needs refinement / not applicable**,
   supporting evidence and named reviewer. Record exceptions/unknowns. A small
   role-recognition trial can compare baseline/after under identical conditions;
   record actual answers, never invented percentage improvement.
6. Run only relevant authorized [mechanical checks](../pipeline/index.md#checks)
   and record results/log paths/current hashes. Source-style coverage, round-trip
   bounds/pose, packed channels and forest freshness are distinct. Existing
   validation without matching hashes is not fresh evidence.
7. Record GLB primitive triangles/material definitions/images/bytes with counting
   convention/hash and explanations for growth. Runtime draw calls/memory/GPU cost
   require separately scoped consumer measurement; mesh sharing alone doesn't prove
   batching. Don't use blanket decimation or texture downsizing as acceptance.
8. **Accept only** a visible predeclared target-size gain without unrelated-rule/
   identity/compatibility regressions, current mechanical evidence and reasoned
   resource changes. Mechanical success never overrides a visual regression.

Regression examples: lost cue/face/facet separation, noisier contacts, glow washout,
palette drift, unmatched evidence, broken grip/clips/origins/endpoints/reuse or
unreasoned resource growth. If no agreed gain after a bounded couple of refinement
iterations, review the rule/recipe/candidate rather than expand an automatic loop.
Manual-edit-loss or compatibility risk stops propagation immediately.

<a id="pilot"></a>
## Pilot and rollout remain separate approval

Proposed small pilot, **not launched/authorized by this skill**:

- Step A: `buildings/archery_range` (B1), `environment/hex_crystal_grove` (F1),
  `characters/knight` (V5): construction, painted environment and older-unit roles.
- Only if Step A is useful/accepted and scope approved: lantern bridge (F5) and
  evil ranged unit (E3); dream menagerie may be a consistency control only.
- Default is no global style/kit/runtime change. A prototype fix needs explicit
  named dependency closure and manual-edit preservation before source propagation;
  don't create unmarked private mesh copies to bypass library checks.
- Keep existing rig/axis/origin/hex/selection/validation guarantees. A renderer/
  game integration or licensed acquisition is not part of this pilot.

Rollout by family only after accepted pilot and additional approval. Preserve
standard/asset baseline versions; restore compatible kit/dependents/maps/exports
as one coherent rollback, not a partially reverted library. Reuse existing galleries/
workers/checks, not a new quality framework. Doc integration should remain reversible
independently of production assets, with no automatic style/paint version bump.
